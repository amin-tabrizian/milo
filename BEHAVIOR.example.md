# Behavior log

This file is the template for `BEHAVIOR.md`. `BEHAVIOR.md` is private: git ignores it, because its log holds the words of the user. To start your own log, copy this file to `BEHAVIOR.md`.

`BEHAVIOR.md` records each behavior issue that the user reports about Milo (how the app looks, moves or responds, and how Milo the agent acts). It also keeps the rules that come from these issues. Code comments and tests refer to log entries as "BEHAVIOR #N".

- **When the user reports a behavior issue,** add an entry to the log (date, the words of the user, the problem, the fix or the status). Then compare it with the rules. If a rule applies, add the entry number to that rule. If the entry shows a new pattern, write a new rule.
- **Before you do UI work or agent-behavior work,** read the rules.

## Rules

1. **Muse is the reference.** Before changing how something looks or moves, look at how Muse does it on the phone and match it: positions, sizes, motion, header. The user compares Milo with Muse side by side.
2. **One motion, no snaps.** A change animates together with what caused it: the keyboard, the menu, a chat opening, a reply arriving. Nothing jumps into place a moment later, and several things don't cut at once.
3. **Never move what the user is touching or reading.** Don't scroll or rebuild under the finger, and follow new content only when the user is already at the end.
4. **Check it the way the phone shows it.** Look at the real iOS surface (Simulator or the phone through iPhone Mirroring), not a mock or desktop browser, before saying it's done. Say plainly what couldn't be checked. iOS keeps colors it saw at launch (the splash set the status bar color).
5. **Restrained look.** Few colors, no black, no bold outlines, no cards or bubbles that differ only in color. Use simple standard icons.
6. **A control shows what it will do.** While something is in progress, its button turns into the standard way to stop it (a stop square), not an alarm color. When it ends, the next control (send) shows at once, with no other icon in between. After dictation's Stop a spinner shows until the last words are in, also with live words already in the box; it never shows while the user types.
7. **Edit, don't duplicate; the user approves changes to their things.** Change the existing task or item in place. Edits to the user's tasks wait for their OK.
8. **Remove what doesn't work on the user's phone** rather than shipping a fallback that sends them elsewhere. Show content in Milo instead of sending the user to another app.
9. **Specific, never generic.** Anything Milo writes for the user (applications, cover letters, outreach) connects the user's real work to the other side's real work, plainly, with no oversold excitement. A tailored resume shows the match through skills and wording, never the company's name or its projects. Showing the connection is how to apply, not a reason to skip (rule 15).
10. **Mind the plan.** Long sessions and big repeated runs burn the shared Claude limit. Keep chats compact and recurring runs short, and let the user see a chat's size.
11. **Text never runs under controls, and nothing scrolls sideways.** Long names, emails, titles, commands and placeholders wrap or end in an ellipsis; the message box stays one line when empty. Test with the longest real value.
12. **Read with scripts, not eyes.** Bulk reading (job lists, posts, big pages) goes through a script that prints a short list. Screenshots are evidence for the user, never input, and never opened back.
13. **Unattended runs never wait on the user.** A scheduled task must not stop on an approval card: commands it needs are allowed by rule, files are written with Write/Edit, and anything that truly needs the user is parked and reported. An unanswered card in an auto-approve task is denied after 10 minutes.
14. **Coming back must just work.** After any navigation (a tab, a sheet, the menu), the chat scrolls and takes typing at once. On iOS don't hide scroll areas with `display: none`; keep them laid out (visibility) and test the way back, not only the way in. A full-screen view opened from a sheet (Milo's browser from Settings) opens over it, so closing it comes back to the sheet, not the chat.
15. **Unattended work finishes the job; it doesn't hunt for reasons to stop.** A run the user left to Milo uses only the hard limits the user set as reasons to skip or stop. Soft judgments (an imperfect match, a crowd of applicants, a long form, a missing account) are not reasons: do the work, make the account, and show the connection. Measure the run by what it finished.
16. **Milo never takes the phone's sound unasked.** No play(), not even a silent clip, until the user plays something or has replies read aloud: any play() stops music in other apps. No AudioContext is kept: iOS starts it again each time the app comes back. Make one only while the mic is open and close it after. A lock or a scroll pauses media; the lock screen can go on.
17. **Standard iOS gestures work.** Pull down closes a sheet or a full-screen picture; pinch and double tap zoom pictures; a swipe right goes back from a page.
18. **Reading never asks.** Anything that only reads or searches (files, mail, calendars, web pages, read-only commands, also in loops, pipes and `find \( \)`) passes without a card; only changes ask.
19. **Memory is global and short; task rules live with the task.** Memory goes into every chat. Keep only lasting facts about the user there. A rule for one kind of work goes into that work's instruction file (the task's own file, or `Instructions/<Topic>.md`), even when the user says "remember".
20. **Milo never shuts itself down.** Milo runs inside the Milo server (with goose and Claude). It restarts the server only with `<restart/>`, which waits for the reply and then brings the server back by itself. A terminal command that kills the server, goose or Claude is blocked (`guard.py`), whatever the permission mode.
21. **An alert opens where it came from.** A tap on a notification opens the chat it is about, whether the app was closed, put away by iOS, reloaded by an update or open on another chat or tab. A link the page loaded on is old news next to a tap. A tap made before the network is back still opens its chat once the Mac answers. Don't rely on iOS telling the app it came back (after a lock it may just thaw the page): a stalled clock counts as a return, and the worker sends the window it brings back to the chat's link. The tap must always bring the app up: the worker focuses or opens a window first, before slow work, and a window it can't focus means it opens one.
22. **Agent behavior is proven live, not assumed.** A change to prompts, `milo_context`, Instructions files, task prompts, tool wiring, tags, memory or compaction gets a matching case in `tests/live/cases.py` and a run of the live suite (CLAUDE.md "Live behavior suite"). A failure is a Milo bug or a bad case; say which, and never reword a prompt just to pass.
23. **Stop stops the work, not only the screen.** Stop must end what runs on the Mac too: goose does not pass a cancel on to Claude Code, so Milo interrupts Claude itself (with its tools and helper agents). Test a Stop by checking that the work ended, not that the reply stopped. A Stop that ends helper agents says so and can be undone for a few seconds.
24. **Milo cleans up after itself on the Mac.** Every process Milo or a session working on it starts ends when it's no longer needed: a goose session's Claude Code (about 400 MB each) closes when the chat moves on or goes quiet, a tab Milo opened closes once it is idle (never the user's own tab, never the one on show), and a `.command` window closes when its script ends. A Mac with 16 GB has no room for leftovers.
25. **The Library holds only what the user keeps.** Milo's scratch output (plots, charts, quick renders) goes to `~/Documents/Milo/Temp` and shows in the chat; it goes into the Library only when the user asks to save it. A browser screenshot for the user goes there too: the folders a tool may write to and the folders the app serves must match.
26. **A server fix isn't live until the bridge restarts.** A change in `web/` reaches the phone at once, but a Python change runs only after a restart, so a page that needs a new route breaks on the old bridge. Check that the running bridge has the change (its start time, or the new route answering with the token) before calling it fixed, and say plainly that a restart is still needed.
27. **A status shows the real state, and every fix the user is told about exists.** "Connected" (or any ok status) comes from a check that it works, not from a saved file. When it stops working, the screen says so in one word and offers the fix in place (Sign in, Retry), without making the user delete and redo it. Before telling the user to tap a button, confirm the button is on the screen in that state. Don't point the user somewhere ("the rest is in the app") unless the rest is there.
28. **Nothing waits for ever.** Every call to another program (an MCP server, Chrome, a web API) has a time limit shorter than goose's 300 s idle timeout. When it runs out, Milo gets a plain error it can act on, the stuck part is restarted or reopened, and a call that may have done something (a click) is never repeated by itself.
29. **One plan, in every place it is written.** A to-do's due date, its planned work blocks (`plan:` in Tasks.md) and its calendar events must agree: a new block, a move or a drop changes all of them in the same turn, and a clear checks them before the chat goes. A question about a day, even a quick spoken one, reads the calendars and the to-do list, and calls planned work planned, not due. A read that fails is said, never answered as free time.
30. **The user's state is the same on every device.** What the user has read, opened or dismissed lives on the Mac, not in one browser's storage, and every open app hears about a change (socket event, plus a check on focus and return). A new marker starts from "already seen" so nothing old lights up.
31. **Milo is one person in one conversation.** What Milo does on its own (scheduled tasks, background work) comes to the main chat as its own message, like a person texting you: no "ran" lines, no steps, no separate chat to look in, and nothing when there is nothing to say. Session plumbing (compaction, token counts, sessions) never shows. Milo knows everything it said in the main chat, whatever produced it.
32. **Plans are checked in code, and the calendar changes only on a yes.** Every plan Milo shows passed `check_plan` against the user's rules (`Instructions/Planning rules.md`), every day answer comes from `day_view` (all sources, or it says which failed), and a calendar event changes only when the user's last message agreed or asked. A full day is full: Milo proposes a move or a drop, never a squeeze. When the user names an exact time, that wins over the rules, and Milo mentions the rule in a few words.
