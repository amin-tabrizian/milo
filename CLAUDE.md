# Milo

Milo is a Muse-style personal agent (a clone of Meta's Muse). Goose runs on the Mac. The phone uses a PWA (`web/`) through Tailscale, or Siri. The goose provider is `claude-acp` (Claude subscription). Overview: README.md; each feature: docs/FEATURES.md; setup: INSTALL.md.md has the features, setup and file map. Read it first.

## Goals

- Muse feature parity. Before you design a UI feature, find out how Muse does it. Look at the Muse app itself on the user's iPhone through iPhone Mirroring on this Mac (see below).
- Minimal UI, always. Few words on screen: a one-word status, an icon or an animation, not a sentence. No walls of text.
- Keep the user's phone working. The live bridge serves `web/` to the phone.
- Behavior issues: BEHAVIOR.md (private, git ignores it; start it from BEHAVIOR.example.md) logs every behavioral issue the user reports, with the rules learned from them. Read its rules before UI or agent-behavior work. When the user reports a new one, log it there and update the rules.

## Look at Muse on the iPhone

- `open -a "iPhone Mirroring"`. It connects only while the phone is locked, and unlocking the phone ends it.
- Keys go to the phone: Cmd+1 Home Screen, Cmd+3 Spotlight (type "Muse", then Return). Cmd+Plus makes the window larger.
- Screenshot: get the window bounds with `osascript -e 'tell application "System Events" to get {position, size} of window 1 of process "iPhone Mirroring"'`, bring it to the front, then `screencapture -x -R x,y,w,h out.png`.
- `screencapture` counts as a screenshot on the phone: Muse opens its "Share to" sheet each time. To watch or time Muse, record the window with `ffmpeg -f avfoundation -pixel_format nv12 -i "3:none"` and crop it to the window bounds.
- Only look. Never send a message or tap an action in Muse. Quit iPhone Mirroring when you are done.

## Run and restart

- `./start.sh` installs what is missing and starts the bridge. Config and token are in `data/config.json`.
- The live bridge can run detached, with its log in `~/Library/Logs/milo.log`.
- A change in `web/` reloads every open phone at once. A change in a Python file needs a bridge restart.
- Before you restart, make sure that no chat is running or compacting: `GET /api/state`, `conversations[].running` and `.compacting`. A restart stops running tasks.
- Restart: stop `server.py`, then from this folder `nohup uv run python server.py >> ~/Library/Logs/milo.log 2>&1 &`. Milo's Chrome (port 9333) continues to run, so its logins stay.
- Milo itself restarts the bridge only with the `<restart/>` reply tag (`Hub.restart_soon`): after the reply and any running chats, compacting and alerts, a detached `restart.py` waits for the old bridge to exit and starts `server.py` again (about 1 s). Milo runs inside the bridge, so a kill from its own terminal ended it mid-turn with nothing to start it again (2026-10-19).
- `guard.py` is a PreToolUse hook (Bash) in Milo's Claude profile (`data/claude/settings.json`, written by `install_guard` at start). It blocks kill/pkill/killall of the bridge, goose or Claude, found as the hook's parent processes. It is a hook because in "Never ask" mode (`auto`, bypassPermissions) no command reaches `on_permission`.
- Never start the bridge from an SSH shell: it can't read the login Keychain (-25308), so Claude says "Not logged in" and Google accounts fail. Over SSH, put the start command in a `.command` file and `open` it: it runs in Terminal, in the desktop session. Terminal closes the window when the script exits cleanly (Basic profile, set 2026-10-21); a failed script leaves its window open, so close it after reading it. Write output to a log and reuse one `.command` file rather than one per run. Check the log for -25308 after a restart. The tests that use the Keychain fail over SSH for the same reason.

## Tests

- `uv run pytest -m "not agent"` runs the unit, API and e2e tests (about 1 minute). Run it after each change.
- The e2e tests use Playwright WebKit at iPhone 15 Pro size, with their own bridge, data and copy of `web/`.
- Big UI changes: develop in a copy of `web/`, serve it with a second bridge (`MILO_WEB_DIR`, own `MILO_DATA_DIR` and port), and run the e2e tests on it with `MILO_WEB_SRC`. Then copy it into `web/`.
- iOS Simulator (no Simulator.app GUI): boot an iPhone with `xcrun simctl boot`, open URLs with `simctl openurl`, take screenshots with `simctl io screenshot`. Tap and type with `idb ui tap/text/key`. To get the soft keyboard, set `defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false`.

## Live behavior suite (how Milo the agent acts)

- **Rule: a change that touches agent behavior is not done until the live suite passes.** Agent behavior means the system prompt and `milo_context` (`build_context`, `VOICE_HINT`, `SCHEDULED_RUN`, `RECENT_MAIN`, `TASK_POSTS` and the compaction prompt in `features.py`), the `Instructions/*.md` files and recurring task prompts (`data/schedules.json`), tool wiring (MCP servers, `google_mcp.py`, `planner_mcp.py`, permissions, `guard.py`), reply tags (`<schedule>`, `<goal>`, `<remember>`, `<suggest>`, `<restart/>`, `<react>`, `<quiet/>`, `<say>`), memory, and compaction. For such a change: add or update the matching case in `tests/live/cases.py` (a new rule or a fixed complaint gets a case, with a "must not" case where it fits), then run the live suite (at least the touched areas, with `--repeat 2` for fuzzy cases) and report the table. A failure is either a Milo bug or a bad case: say which, and never reword a prompt just to make a case pass.
- Run: `uv run python tests/live/run.py` (all cases), `--case <id>[,<id>]`, `--area email,schedule`, `--repeat N` or `--repeat-fuzzy N` (flakiness), `--no-judge`, `--list`, `--keep` (keep the sandbox). It prints a pass/fail table with reasons and saves `reports/live/<time>.md` and `.json` (and `latest.md`; `reports/` is gitignored). The same cases run as pytest: `uv run pytest -m agent tests/test_agent_behavior.py`.
- Cost: about 31 cases in 8-12 minutes, 5-50 s each; each turn is a real goose session on the Claude plan (about 20-60k tokens, more for multi-turn email cases), plus a few judge calls (`claude -p`, Sonnet). Mind the plan: run the touched areas while working, the whole suite before calling it done.
- How it works: `tests/live/bridge.py` runs the real `server.py` (same Hub, prompts, `milo_context`, tags and goose/claude-acp sessions, Milo's own Claude profile and model) on port 8799 with a sandbox from `sandbox.py`: temp copies of Library (Planner, Health Tracker, Recurring tasks, CV), Instructions, Jobs/*.md, memory, goals and schedules, with paths rewritten to the copies. Each case starts from the same copies in a fresh chat. Graders read the raw reply (with tags), the hook's log of every tool call, the fake Google calls and the file diffs; an LLM judge only grades fuzzy things (tone, "did it ask").
- Safety: no real side effects. milo-google is faked in-process (`fake_google.py`: fixed mail and calendar around today; sends, drafts and event changes are recorded, never made). The claude.ai connectors (Gmail, Calendar, Slack, Drive) are off (`ENABLE_CLAUDEAI_MCP_SERVERS=false`) and blocked. A PreToolUse hook in the sandbox's project settings (`tests/live/hook.py`) logs every call and blocks writes outside the sandbox, kills and restarts, network sends, sub-agents and crons. No pushes, no scheduler firing, no browser, and `<restart/>` is only recorded. The browser and the browser status checks are not covered (no browser in the sandbox).

## Facts that are not clear from the code

- Approvals with `claude-acp`: approval requests reach the ACP client only if `goose acp` starts with `GOOSE_MODE=smart_approve` or `approve` in its environment. `session/set_mode` after start has no effect. `auto` means Claude's bypassPermissions. To change the mode, Milo restarts goose.
- Under `smart_approve`, Claude Code does not ask before it writes files in `goose_cwd`.
- goose's Claude runs with `CLAUDE_CONFIG_DIR=data/claude` (Milo's own profile), set in `acp.py`. Without it, goose inherits the profile of the shell that started the bridge and shares its memory. The Keychain sign-in is keyed by that path, so a moved folder needs `claude auth login` again.
- `goose_cwd` is `~/Documents/Milo`, not home: in home, Claude loads `~/.claude` as project settings. The code must not be `goose_cwd` either, or Claude loads this file. On macOS `~/Documents/milo` is the same folder as `~/Documents/Milo`.
- `GOOSE_MODEL` is set in Milo's environment for goose. It overrides the model in `~/.config/goose/config.yaml`.
- ACP `session/new` `mcpServers` (`{type: "http", name, url, headers: [{name, value}]}`) go through goose to `claude-acp`. The Claude Code permission title for these tools is `mcp: <server>  <tool>`.
- workspace-mcp binds its stdio session to the first Google account that uses it. It refuses other accounts, and it looks like they are signed out. `GoogleTools` starts a new session when the account changes. Do not remove this.
- iOS 27 Safari makes `window.innerHeight` smaller when the keyboard opens. To find the keyboard, use `documentElement.clientHeight - visualViewport.height`.
- Keyboard timing (iOS 26 Simulator): a focus at the bottom of the screen makes iOS slide the whole page up, and `visualViewport` reports the new size 180-320 ms late. The message box therefore focuses itself with `focus({ preventScroll: true })` on touchend, and `moveApp` starts the move on focus from the last keyboard height (`kbH` in storage). The keyboard's curve is about `cubic-bezier(.25,.6,.3,1)` over 280 ms (`--kb-curve`).
- Tokens: every step of a turn re-reads the whole session, so a long session costs more on every message. A chat's goose session (`conv.sid`) can differ from its id. Compacting (`Hub.compact`: the old session writes a summary, a new one starts from it) runs after a turn that leaves the chat over `compact_at` (100k) tokens. It is silent (BEHAVIOR #93): the chat keeps its messages and shows nothing, the app has no compact control or token count, and "compact" is an ordinary message. `POST /api/conversations/<id>/compact` exists only for the live suite. Old chats may still hold `kind: "compact"` notes; the app hides them. Inside a turn, Claude Code compacts by itself past `autoCompactWindow` (140k), which `install_token_settings` writes into Milo's profile together with the denied tools and the skills that are off (the base prompt went from about 17.5k to 12.7k tokens). Each run of a recurring task starts a new session. Each goose session keeps its own claude-agent-acp and Claude Code processes (about 400 MB) until it is closed: `Hub.release_sessions` closes old sessions and side chats quiet for 15 min (`RELEASE_IDLE`) every minute, and their next prompt loads them again with their history. Without it 32 sessions filled the 16 GB Mac and it hung (2026-10-21). goose reports the context size in `usage_update` (`used`).
- Push alerts: `Hub.notify` sends a text of more than 8 words as one line of a few words, written by `notice_model` (Haiku, `run_claude`) in a background task. The phone shows it about 3 s later. If the model fails, the start of the text goes out.
- Tapping an alert (sw.js `notificationclick`, `Tap` in app.js): iOS may start the app on "/", reload a page it put away on its last `#c=` link, or bring the app back before the worker runs. iOS may also thaw a page after a lock with no `visibilitychange`. The worker leaves a note in the cache (`milo-open`), messages every window, focuses one and sends it to the chat's `#c=` link (or opens a window when there is none); the app reads the note on start and for 5 s after each return (`resumed`: visibilitychange, pageshow, or its clock stalling), and a tap beats the link the page loaded on. Playwright WebKit empties CacheStorage on reload, so tests put the note back with an init script.
- Chat titles (on `title_model`, Haiku) and ideas use `run_claude` (feed.py): `claude -p` with no tools, about 4k tokens of overhead. A goose session starts at about 17k.
- Milo's Chrome tabs: a tab that opens while Milo works (a chat runs or the feed reads) is Milo's (`BrowserManager._milos`). `Hub.close_tabs` closes them each minute once Milo is idle, keeping the tab on show and the last tab, then `BrowserTools.select_shown` moves Playwright MCP back to the tab on show (it falls back to a neighbour when its own tab closes). Tabs opened while Milo is idle are the user's and stay. The "Google Chrome Helper (Aperitif ...)" processes are this Chrome.
- milo-browser drops the image from a `browser_take_screenshot` that has a `filename` (`saved_only`): evidence is for the user, and an image in context is re-read on every later step.
- Playwright MCP lists every open tab after each action. milo-browser keeps that list only when the tab count or the current tab changes (`_trim_tabs`): on a long form it was nearly half of every result.
- Playwright MCP only reads and writes files under its working folder and its `--output-dir` ("outside allowed roots"). Milo runs it in the Library (`files_dir`), so uploads and saved screenshots must be Library paths. Snapshots stay in `milo/.playwright-mcp`.
- When a turn ends, goose/claude-acp sends again the permission requests it already asked in that turn (as new cards; they don't run). `on_permission` answers a repeated command with the user's earlier answer (`Hub.answered`, cleared when a turn starts).
- Permission titles from claude-acp write the MCP tool with spaces ("mcp: milo-google  send gmail message"). `classify` joins them with `_`. Sending email always asks; no rule can allow it.
- A recurring task with `auto_approve` (in `data/schedules.json`; set with `PATCH /api/schedules/<id>`) runs its chat's risky browser actions (uploads, Submit clicks) without asking. Clicks that spend money still ask. A card it raises anyway is denied after `unattended_approval_minutes` (10) without an answer. The app has no switch for it yet.
- Scheduled tasks talk in the main chat (BEHAVIOR #93). Each task (recurring or one time) runs in a hidden chat of its own (`conv.schedule`, `Hub.schedule_conversation`; the app leaves it out of the menu and its dots), with a new session each run. Only the reply's answer (the text after the last tool call; `SCHEDULED_RUN` tells Milo so) goes to the main chat, as Milo's own message (`Hub.post_to_main`, a `message` event; `from_task` names the task; weather cards come along, steps do not). The post waits for the main chat's running turn. It also goes in the main chat's `inbox`, which `_prompt_blocks` sends once as `TASK_POSTS` with the next prompt, so the main session knows what it said. Quiet, failed and stopped runs post nothing (the run history in Upcoming says it). Alerts from a task chat open the main chat (`chat_id`), and its approval cards show there (`approvalChat` in app.js). `auto_approve` and the Library result files still key on the task's hidden chat.
- Planning runs through milo-planner (`planner_mcp.py`, BEHAVIOR #94): `day_view`, `check_plan`, `workload` and `plan_block`. The rules are values in `Instructions/Planning rules.md` (`load_rules`; missing ones fall back to `DEFAULT_RULES`). Tasks.md lines are parsed by `parse_tasks`: due date in the second field, `plan:` blocks as "Wed 11-11 15:00-17:00", `est: 3h` (or "needs 3-4 h"). A personal-calendar event at the same time as a `plan:` block shows once, as planned work. The work feed is `busy_url` in `data/config.json` (none: no work meetings, not a failure). The live suite fakes it (`busy_days` in `tests/live/bridge.py`, a case's `setup["busy"]`).
- Calendar writes are guarded in code (`Hub.calendar_guard`, from `google_guard`): `manage_event` (but an RSVP) and `plan_block` run only when the user's last message agrees or asks (`SAYS_YES`, not `SAYS_NO`), and never in a scheduled run. "Plan my day" is not a yes. An unknown MCP key is let through.
- There is no clear (removed 2026-11-11, BEHAVIOR #95): no "clear" word, menu item, Siri command or endpoint, and no mop or dust animation. Old chats' `data/cleared/*.jsonl` files stay as they are.
- There are no reminders (removed 2026-10-22): every scheduled item is a task (`kind: "task"`) that runs an instruction. "Remind me" goes to the Library's `Planner/Tasks.md` (`TASKS_CONTEXT`), and the "Due today" task lists what is due at 14:30. `Scheduler` drops any other kind it finds on load, so old data can't fire.
- Milo changes an existing task with `<schedule id=... cron/when/title>`. The change waits for the user's OK on an approval card (`Hub.confirm_schedule_edit`) and keeps the item's id, chat, run history and `auto_approve`. Pause and resume (`enabled`) apply at once.
- goose returns `stopReason: "cancelled"` for many tool turns that finished normally; Claude's transcript shows no interrupt. Milo treats a turn as stopped only after `Hub.cancel` (the user's Stop) sets `conv.stopping`.
- Settings' Claude usage comes from `claude -p /usage` on Milo's profile (`/api/usage`, `parse_usage`). It is a local command: no model turn, no tokens. The limits are for the whole account, so Claude Code and claude.ai on the personal account count too.
- Pictures in replies (`![title](path)`, also a full path with spaces) load from `GET /api/picture?path=`. It serves only picture files (`features.IMAGE_SUFFIXES`) inside the Library or Temp (`~/Documents/Milo/Temp`, `temp_dir` in config; `features.find_picture`). Plots go to Temp (`PICTURES_CONTEXT`), and `clean_temp` removes files older than 30 days every hour. BEHAVIOR #76.
- Memory (`data/memory.md`) is sent in full with every chat, so it holds only short, global facts about the user. Task rules go in instruction files (a recurring task's own file, such as `Jobs/apply.md`, or `Instructions/<Topic>.md` next to the Library). `build_context` sends only the index of `Instructions/` (file name and first line).
- Motion for the header dog's look (`mascot.js` `gaze`): iOS sends `deviceorientation` only after `DeviceOrientationEvent.requestPermission()` is called from a tap (touchend or click; the end of a scroll is refused). app.js asks on the first tap of each launch. iOS shows its prompt only the first time and answers later calls at once. A "no" is not kept: the next launch asks again (keeping it once left the dog still for good). Without the tilt the dog follows a finger anywhere on the screen; with it, only a finger within 200 px.
- iOS restarts the motion sensor after a pause, and `alpha` then starts from 0 again wherever the phone points (WebKit uses CoreMotion's arbitrary-north frame). `gaze` treats a gap, a jump of more than 30 degrees between two readings, and the first 0.3 s after a start as a new start.
- Screen orientation: iOS 26 Home Screen web apps turn with the phone. They ignore the manifest's `orientation`, even when the icon is added fresh, and `screen.orientation.lock` does not exist (checked in the iOS 26.3 Simulator). Milo can't keep itself in portrait.
- Reply tags (`<remember>`, `<schedule>`, `<goal>`, `<suggest>`) are removed on the server (`features.py`) and, during streaming, in `stripDirectives` in `web/app.js`. If you add a tag, update both.
- Siri (`POST /api/ask`): the Shortcut reads only the reply's `<say>` part (`SIRI_HINT`, `extract_say`, `siri_answer`). The tags come out but their words stay in the chat, as the start of the reply; the bridge adds `SIRI_MORE` ("The details are in your Milo chat.") only when the chat has more than the spoken part (BEHAVIOR #90).

## Rules

- `data/` has secrets (access token, VAPID key, Google tokens, browser profile). Never commit it, and never send it outside this Mac. Account passwords, 2FA secrets and the Google client secret are in the macOS Keychain (service "Milo").
- Real people's names and emails, the user's private details (address, health, immigration status, weight), and the Mac's host, tailnet and user names, never go into git. The files on this Mac keep the real text; a git filter (`private.py`, set up with `python3 private.py install`) puts the fake text from `data/private.json` in each commit and the real text back on checkout. When you add a new real name, email or private detail to a tracked file, add a `[real, fake]` pair to `data/private.json` (a fake that is not in the code yet, `tests/test_private.py` checks it), then run `git add --renormalize .`. The pre-commit hook refuses a commit with a known real value, but it cannot know a new one.
- **Check for personal data before every push to GitHub.** The repo is public. Before `git push`, run `python3 scripts/check_private.py --all` and read every hit; the pre-push hook (`.githooks/pre-push`, enabled with `git config core.hooksPath .githooks`) runs the same check on what is pushed, files and commit messages, against `data/private_terms.txt` (gitignored). A hit means fix the file or the commit, never `git push --no-verify`. When a new real name, email, place, account or personal topic shows up in the work, add it to `data/private_terms.txt` first. Commit messages follow the same rule. Private material goes in gitignored files with a tracked template (`BEHAVIOR.md` and `BEHAVIOR.example.md`).
- Keep the code style of each file. Comments are short and say why.
- User-facing text: plain and short. No emoji in the UI text that you write.
